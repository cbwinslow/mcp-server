# MCP Server + Knowledge Graph Platform Implementation Plan

## 1. Architecture & Components

### Containerization Baseline
- **Primary choice**: Docker Compose (for single Ubuntu host deployment)
- **Future path**: k3s orchestration (for scaling)
- **Rationale**: Docker Compose provides simple, production-ready deployment for single node with clear path to k3s

### Services Architecture

#### Core Services
1. **Supabase (Postgres)**
   - Full self-hosted Supabase stack:
     - Postgres database with pgBouncer
     - Supabase services (auth, storage, functions)
     - Studio admin UI
     - Kong API gateway (included with Supabase)

2. **Neo4j**
   - Community Edition (sufficient for initial requirements)
   - Plugins: APOC, GDS (Graph Data Science)
   - Optional: Bloom (if license available)

3. **Kong API Gateway**
   - Use Supabase's Kong instance primarily
   - Add dedicated Kong if more complex routing needed

4. **MCP Server (FastAPI)**
   - Migrated to async SQLAlchemy with Postgres
   - Alembic for migrations

5. **Workers**
   - Ingestion workers (crawler, extractor)
   - Embeddings generation workers

6. **LlamaIndex Services**
   - Hybrid retrieval service
   - Knowledge graph sync workers

### "Need vs Don't Need" Assessment

#### Essential Services (Need)
- Postgres (Supabase) - Core data storage
- Neo4j - Graph database for knowledge representation
- Kong - API gateway for security and routing
- FastAPI MCP Server - Core API
- Workers - Processing pipeline
- LlamaIndex - Hybrid retrieval and KG integration

#### Optional Services (Don't Need Initially)
- Bloom - Visualization (can use Neo4j Browser)
- Vector DB (separate) - Use pgvector in Postgres
- MinIO - Object storage (can use Supabase storage)
- Enterprise Neo4j - Community edition sufficient for MVP

## 3. LlamaIndex Integration Strategy

### Integration Architecture

#### Hybrid Retrieval Approach
1. **Postgres + pgvector** for structured data and initial filtering
2. **Neo4j** for relationship-based queries and graph analytics
3. **LlamaIndex** as orchestration layer for:
   - Hybrid search (vector + keyword)
   - Knowledge graph synchronization
   - Query routing based on intent

#### Key Integration Points

1. **Data Ingestion Pipeline**
   ```
   GitHub Repo → Crawler → Extractor → LlamaIndex Processor → 
   [Postgres (structured data + embeddings)] + [Neo4j (graph relationships)]
   ```

2. **Query Processing Pipeline**
   ```
   User Query → LlamaIndex Router → 
   [Vector Search (pgvector)] OR [Graph Query (Neo4j)] OR [Hybrid] → 
   Results Aggregator → Response
   ```

### pgvector vs Neo4j Tradeoffs

#### pgvector (Postgres)
**Pros:**
- Integrated with existing data storage
- ACID compliance
- Familiar SQL interface
- Good for initial filtering and structured queries
- Easier backup/restore

**Cons:**
- Limited relationship querying
- Less efficient for complex graph traversals
- Scaling challenges with high-dimensional vectors

#### Neo4j
**Pros:**
- Native graph capabilities
- Efficient relationship traversal
- Powerful graph algorithms (via GDS)
- Semantic querying with Cypher
- Better for knowledge representation

**Cons:**
- Separate system to maintain
- Different query language (Cypher vs SQL)
- More complex backup/restore

#### Recommendation
Use **both** with LlamaIndex as the orchestration layer:
- pgvector for initial filtering and similarity search
- Neo4j for relationship discovery and graph analytics
- LlamaIndex to intelligently route queries and combine results

### LlamaIndex Components

1. **Indexing Service**
   - Repository document processors
   - Code element extractors
   - Embedding generators
   - Knowledge graph updaters

2. **Query Engine**
   - Intent classifier (vector vs graph vs hybrid)
   - Query routers
   - Result synthesizers

3. **KG Sync Service**
   - Periodic sync from Postgres to Neo4j
   - Relationship discovery algorithms
   - Entity resolution

## 5. Security, Networking, and Observability Strategies

### Security Strategy

#### Secrets Management
1. **Primary**: Bitwarden Secrets Manager (as currently implemented)
2. **Backup**: SOPS with AWS KMS for critical infrastructure secrets
3. **Runtime**: Docker secrets for container-level secrets

#### Authentication & Authorization
1. **API Authentication**:
   - JWT tokens via Supabase Auth
   - Kong API key validation for service-to-service
   - OAuth2 integration for external services

2. **Database Security**:
   - Role-based access control (Postgres roles)
   - Connection pooling with pgBouncer
   - Encrypted connections (TLS)

3. **Network Security**:
   - Internal service communication only (no direct external access to DB)
   - Kong as sole entry point with rate limiting
   - Firewall rules on Ubuntu host

#### Code Security
1. **Static Analysis**:
   - Bandit for Python security scanning
   - Semgrep for custom rule checking
   - Dependabot for dependency vulnerability monitoring

2. **Runtime Security**:
   - Container image scanning with Trivy
   - Runtime monitoring with Falco

### Networking Strategy

#### Internal Network
- **Default network**: Docker default bridge network
- **Service discovery**: Docker DNS (service names)
- **Inter-service communication**: HTTP/gRPC with service mesh consideration for future

#### External Access
- **Kong Gateway** as single entry point:
  - `/api/*` → MCP Server
  - `/db/*` → Supabase REST
  - `/graph/*` → Neo4j (if exposed)
  - `/studio/*` → Supabase Studio
  - `/llm/*` → LlamaIndex Service

#### TLS Strategy
1. **Internal**: Self-signed certificates with internal CA
2. **External** (if needed): Let's Encrypt with DNS challenge
3. **Implementation**: Kong handling TLS termination

#### Network Policies
1. **Ingress**:
   - Only Kong ports exposed externally (80, 443, 8000, 8443)
   - Rate limiting and IP whitelisting where appropriate

2. **Egress**:
   - Internet access only for crawler and external API calls
   - Internal service communication restricted

### Observability Strategy

#### Logging
1. **Centralized Logging**:
   - Loki for log aggregation
   - Promtail for log shipping
   - Structured JSON logging from all services

2. **Log Structure**:
   ```json

   ```

#### Monitoring
1. **Metrics**:
   - Prometheus for metrics collection
   - Node exporter for host metrics
   - Custom application metrics (processing rates, error rates)

2. **Health Checks**:
   - Liveness probes for all services
   - Readiness probes for critical services
   - Custom health endpoints in MCP server

#### Tracing
1. **OpenTelemetry**:
   - Distributed tracing across services
   - Trace context propagation
   - Integration with logging and metrics

#### Alerting
1. **Critical Alerts**:
   - Service downtime
   - High error rates
   - Resource exhaustion

2. **Warning Alerts**:
   - Slow processing times

#### Visualization
1. **Grafana**:

## 7. Risks and Mitigations

### Technical Risks

1. **Data Migration Complexity**
   - Risk: Data loss or corruption during SQLite to Postgres migration
   - Mitigation: Comprehensive backup, validation scripts, and rollback plan

2. **Performance Bottlenecks**
   - Risk: Neo4j or Postgres becoming bottlenecks at scale
   - Mitigation: Load testing, query optimization, and horizontal scaling plans

3. **Integration Failures**
   - Risk: LlamaIndex, Neo4j, and Postgres not working cohesively
   - Mitigation: Thorough integration testing and staged rollouts

### Operational Risks

1. **Secrets Management**
   - Risk: Exposure of sensitive credentials
   - Mitigation: Use Bitwarden with proper access controls and audit logs

2. **Backup Failures**
   - Risk: Inability to recover from data loss
   - Mitigation: Regular backup testing and multiple backup locations

3. **Monitoring Gaps**
   - Risk: System failures going undetected
   - Mitigation: Comprehensive alerting and regular monitoring reviews
